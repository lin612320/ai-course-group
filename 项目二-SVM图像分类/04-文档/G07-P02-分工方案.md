## 2　代码边界与唯一作者原则（防冲突的核心）

公共模块 `config.py`、`model.py`、`train.py`、`test.py`、`utils.py`、`visualize.py` **只有组长有写权限**。其他人需要新增特征或候选时，在组内发一句《改动申请》：改什么、影响哪些 Task、怎么验证。组长实现并跑通 `checks` 后回复。

每个 Task 的实验一律通过命令行参数与 `--output` 目录隔离，**不靠改默认值区分实验**：

| 实验 | 输出目录 | 说明 |
|---|---|---|
| Task 1 | `results/task1` | 只 validate |
| Task 2 | `results/task2` | validate → refit → test |
| Task 2 自主策略 | `results/task2_strategy` | 与上表分开，避免覆盖 |
| Task 3 | `results/task3` | validate → refit → test |
| Task 3 扩展 | `results/task3_extended` | validate 加 `--extended`，后两步不加 |

谁都不许覆盖别人的 `results/`；同名结果重复运行即覆盖，只影响自己。

### 2.1　谁写谁不二审（组长兼任维护者的配套约束）

组长既是公共模块维护者，又是 Task 3 策略特征的作者。为防止「自己写自己验」，加一条硬约束：

- 凡组长改过 `model.py`、`train.py`、`test.py`、`config.py`（含特征注册表、新特征、新候选），**合入后由张文璟跑一遍 `checks` 全绿 + 与改动前的 Task 1 验证准确率逐位比对**，两项结果贴在群里；不一致就回滚，不解释。
- 张文璟对组长改动的验证只判「有没有破坏既有行为」，不改代码、不提方案。
- 其他人（李行加特征、周以撒/张文璟提改动）仍走《改动申请》，由组长实现——这一侧不受影响。

### 2.2　组长的 P0 任务：先开一次扩展点（0.5 天，前置）

在 `model.py` 增加特征注册表（`pixels` / `hog` / 自定义函数名 → 函数），使后续新增特征只加一行注册 + 一个独立函数文件，不动 `build_pipeline` 主体。验收：`checks` 5 项全过，且 Task 1 验证集准确率与重构前完全一致（同一台机器、同一种子，数字逐位相同；张文璟复核）。
「最小闭环」原则：扩展点没通之前，谁都不许开工自己的实验。

## 5　运行命令对照（照抄即可，注意 `--output` 区分）

```powershell
# 环境
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt

# 流程自检（公共模块有任何改动后必跑）
python -m unittest discover -s checks -v

# 周以撒：Task 1
python main.py --task 1 --stage validate

# 张文璟：Task 2
python main.py --task 2 --stage validate

python main.py --task 2 --stage test

python main.py --task 2 --stage refit    --output results/task2_strategy
python main.py --task 2 --stage test     --output results/task2_strategy

# 林子航：Task 3（数据用官方四个 IDX.gz 文件目录，免下载）
python main.py --task 3 --stage validate --data-dir "../../06-资源/数据/fashion"
python main.py --task 3 --stage refit    --data-dir "../../06-资源/数据/fashion"
python main.py --task 3 --stage test     --data-dir "../../06-资源/数据/fashion"

# 林子航：Task 3 扩展（只有 validate 带 --extended）
python main.py --task 3 --stage validate --extended --output results/task3_extended --data-dir "../../06-资源/数据/fashion"

python main.py --task 3 --stage test   --output results/task3_extended --data-dir "../../06-资源/数据/fashion"
```

阶段一致性是硬性的：`validate`、`refit`、`test` 三次必须用同一 `--output` 与同一数据选项，否则 `refit_manifest.json` 的指纹校验会直接拒绝。

## 6　明确不做（防范围蔓延）

- 不手写 SVM 求解器，不引入 CNN / 深度学习框架
- 不改官方 60000/10000 划分，不重采测试集
- 不拿测试集调参；最终测试只评一次，出结果后不回头改方案
- 不在 `config.py` 里改默认值来区分实验（一律命令行 + 独立目录）
- 公共模块只由组长改；其他人一律提《改动申请》，不自己在本地改完再合
- 报告不写无法核对的数字：每个数字都要能指到 `results/` 下某个文件

新想法记进 backlog，不进当轮交付。

## 7　已知风险与预案

| 风险 | 预案 |
|---|---|
| 自主策略做不出提升 | 如实记录（任务书允许），并写清已排除的方向；不为了「好看」反复用测试集试 |
| 标准化组结论被误读 | 由张文璟在方法段写死 gamma 取法，分析段必须先讲 gamma 尺度再讲标准化 |
| 两人数字打架 | 交叉复核制：周以撒↔张文璟、李行↔林子航；以 `results/` 文件为准，不以截图为准 |
| 组长兼维护者成为瓶颈 | 李行、周以撒、张文璟的《改动申请》集中在阶段 0–1 提；阶段 2 起冻结公共模块，只允许不改公共模块的实验 |
| 维护者自审自证 | 见 2.1：组长改动一律由张文璟跑 `checks` + 数字比对，不一致即回滚 |
| HOG 反复重算拖时间 | 8000 张 HOG 每次提取约十秒级；候选多时先固定 HOG 参数、只扫 C，必要时缓存特征到临时目录（缓存不进提交包） |
| 数据来源存疑 | 核对 IDX 四文件形状与类别计数（60000/28×28、10000/28×28、每类 6000/1000）；`data_source.json` 记录文件路径与指纹 |
| 时间不够 | 砍扩展实验（Task 3 `--extended`）与统一出图美化，保三个 Task 的主线数字与报告完整性 |
